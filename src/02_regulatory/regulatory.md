# 국가별 인허가 규제

## 1. 페이지 목적

화장품 OEM·ODM 해외영업 담당자가 성분을 직접 검색하거나 개발요청서·성분표를 이 페이지에 업로드하여, 대상 시장의 성분 규제 정보와 추가 확인 사항을 조회한다.

- **문서 성격**: 이 문서는 `/regulatory` 페이지 기능 구현의 기준 명세이다. 기능 요구사항은 README 규칙에 따라 이 문서를 최우선으로 따른다. 현재 성분 직접 검색(한글·영문 INCI 검색·입력 중 자동완성·후보 선택·시장별 규제 조회·결과 카드)과 파일 탭의 **업로드 → 시트 선택 → 성분·함량 추출 → 확인·수정 → 성분 확인(식약처 DB 후보 검색) → 사용자 선택 → 선택 성분 규제 일괄 조회 → 결과 표·상세**(텍스트 PDF·.xlsx)는 구현되어 있다. 스캔 PDF·PNG/JPG 이미지는 서버 로컬 OCR(Tesseract)로 읽어 같은 흐름에 연결된다(2026-09-23). 중간 포함 검색, 함량 기준 비교(검토 상태), 시장 자동 선택은 **미구현** 상태이다.
- **현재 구현 기준 (2026-11-11, K-Beauty 제거 4-1~4-3단계)**: 규제 화면(직접 검색·파일 일괄 조회)과 챗봇의 성분 규제 기능은 모두 **식약처 성분 DB(화장품 원료성분정보)·규제 DB(화장품 사용제한 원료정보)를 읽기 전용으로** 쓴다 — 후보 검색 → 사용자 선택 → 국가별 규제 조회. Route 는 `/api/regulatory/search` · `/lookup` · `/extract` 뿐이다. 외부 규제 API 호출이 없고 K-Beauty(RapidAPI) 설정이 필요하지 않다 — 관련 모듈·응답 기록·테스트·설정은 4-3단계에서 삭제했다. 현재 Route·화면 동작은 `api_reference.md` 1·3장, 챗봇은 `src/06_chatbot/chatbot.md` 7-1 이 기준이다. DB 수집은 별도 스크립트로만 하며(`MFDS_API_KEY` 필요) 앱 시작·요청 때 수집하지 않는다. 조회에는 수집이 끝난 DB 파일이 필요하다.
- **다음 기능 (설계 단계·미구현, 2026-11-13)**: 선택한 규제 내용 저장·담당자 메모(`regulatory_notes`) 설계는 17장. 코드·마이그레이션·DB 변경 없음.
- **확정 요구사항**: 아래에서 별도로 확인 예정·협의 사항으로 표시하지 않은 기능은 초기 구현 목표이다. PDF(텍스트·스캔), Excel(.xlsx), 이미지(.jpg·.jpeg·.png)를 모두 포함한다.
- **범위 제외**: 문서 전체 분석·요약·번역·개발요청서 생성, 다른 담당자 페이지와의 파일 연동, 성분 조합의 안전성·규제 적합성 자동 판정.
- 결과는 조회된 근거와 입력 조건의 비교를 지원한다. 최종 수출 가능 여부, 제품 전체의 적법성 또는 안전성을 확정하지 않는다. 부분 개발요청서는 완성 처방으로 취급하지 않는다.
- **사전검토 보조 도구 (2026-09-25 명시)**: 이 페이지는 해외영업 담당자가 성분 규제를 사전검토하는 보조 도구이며, 최종 처방과 수출 대상국 규정의 적합성은 연구·규제 담당자가 검토한다. 대시보드에서 조회되지 않는 성분이나 더 자세한 제한사항은 식약처 공식 조회 페이지(의약품안전나라 ‘화장품 사용제한 원료’, `https://nedrug.mfds.go.kr/pbp/CCBDF01`)로 연결해 사용자가 직접 추가 확인한다. 조회 결과가 없다고 사용 가능하거나 규제가 없다는 뜻이 아니며, 식약처 사용제한 원료 조회만으로 모든 해외 시장의 적합성이 확정되지도 않는다. ‘최신 규제 검증 완료’·‘수출 가능’ 같은 단정 문구는 쓰지 않는다.
- **확인 예정**: 아세안 공통·개별 국가 규정 범위, 추출 도구 및 운영 제한 값은 확인 예정이다. (배포용 성분 DB·규제 DB 사본은 2026-11-13 5-1단계에 `data/regulatory/` 에 준비됨 — 실제 운영 배포 적용은 미완료) 확인 전에는 해당 범위를 제공한다고 단정하지 않는다.

**파일 위치 원칙**

- 기능 코드, Python 모듈, API 설명, 응답 예시, 테스트 코드, 샘플 문서는 모두 `src/02_regulatory/` 안에 생성한다.

- `src/` 안의 `.json`·이미지·CSS·JS 등은 `/assets/<경로>`로 브라우저에 공개될 수 있다(Python·MD 는 제공하지 않음). 따라서 `samples/`, `tests/fixtures/`에는 비밀값(API Key, 요청 헤더 값 등)과 민감한 실제 문서(실제 고객·바이어 개발요청서, 처방 정보 등)를 넣지 않는다. 샘플은 직접 만든 가상 문서나 공개 가능한 자료만 사용한다.
- 사용자가 실제로 업로드한 원본과 처리 중 임시 파일은 `src/` 등 공개 자산 경로에 저장하지 않는다. 저장 위치는 13항을 따른다.

## 3. URL

- 기존 페이지 URL은 `/regulatory`, endpoint는 `regulatory`이며 변경하지 않는다.
- 새로 추가하는 API Route는 `/api/regulatory/` 접두사를 사용한다.
- 성분명 후보 검색, 파일 추출 요청, 국가별 규제 조회 요청은 각각 별도 처리로 구분한다. 세부 Route, HTTP 메서드, 요청·응답 계약은 구현 시 확정하여 `src/02_regulatory/api_reference.md`에 기록한다. 이 문서의 화면 항목은 Route 계약을 의미하지 않는다.
- 페이지 이동과 정적 자산 경로는 기존 `url_for()` 방식을 사용한다.

## 4. 사용자

- 화장품 OEM·ODM 해외영업 담당자: 바이어 요청 성분·함량·제품 조건을 확인하고 대상 시장의 근거 자료와 추가 확인 사항을 검토한다.
- 직접 검색은 개별 성분 확인에, 파일 일괄 조회는 개발요청서·성분표에 기재된 여러 요청 성분 확인에 사용한다.
- 규제 정보가 조회되었다는 사실과 해당 입력이 기준을 충족한다는 의미를 구분해 이해할 수 있어야 한다. 검토 범위와 미확인 사항을 결과에 함께 표시한다.

## 5. 주요 기능

**성분 직접 검색**

- 탭 안에서 국가/시장을 선택하고 한국어 성분명 또는 영문 성분명(INCI)을 입력하여 검색 버튼으로 조회한다. 두 언어 지원은 확정 구현 목표이다.
- 입력 앞뒤 공백을 제거하고 영문 검색은 대소문자를 구분하지 않는다. 검증된 한글명·영문명·동의어를 동일 성분에 연결하며 AI 번역만으로 성분의 동일성을 확정하지 않는다.
- 직접 검색의 입력은 성분명과 국가/시장뿐이다. 함량·제품 유형·사용 조건 입력과 기준 비교(검토 상태)는 직접 검색에서 제공하지 않는다. (2026-09-23 요구사항 변경. 함량 추출·수정·비교는 파일 일괄 조회 요구사항으로 유지)
- 결과는 성분명·영문명·조회 시장·조회 상태·규제 유형과 규제 조건을 표시한다. 규제 조건은 API 원문(`limit_condition`)을 결과 카드 본문에 충분한 폭으로 보여주고, 원문 구조가 명확히 구분되는 경우에만 언어별(영문 전체가 위, 한국어 전체가 아래. 한 언어만 제공되면 그 언어만)로 배치한 뒤 적용 제품·최대 농도·사용 조건·주의 문구로 나눠 표시하고, 분류가 불확실한 내용은 ‘기타 원문’에 누락 없이 둔다. 번역·요약은 하지 않으며 한국어 문장 안의 영문 성분명·단위를 분리하지 않는다. 수치·단위·레티놀당량 같은 기준과 적용 제품의 대응 표기((a)/(b) 등)는 원문 그대로 보존하며, 구분이 불확실하면 요약하지 않고 원문을 읽기 좋게 표시한다. 특정 성분에 맞춘 조건을 하드코딩하거나 API에 없는 정보를 생성하지 않는다. 출처·날짜·원문 전체는 상세 Modal에서 확인한다.
- **확인 사례 (2026-09-23)**: 한글 검색 `/v1/ingredient/kr?q=`와 영문 INCI 검색 `/v1/ingredient/inci?q=`는 공개 README 문서와 실제 호출로 확인했다(9항). 둘 다 **시작 일치**이며 영문은 대소문자를 무시한다. 한글 엔드포인트에 영문을 넣으면 0건이므로 서버가 입력의 한글 포함 여부로 엔드포인트를 골라 **1회만** 호출한다. 검색어 최소 길이는 API 문서 기준 2글자다.
- **확인 예정**: 동의어 범위·식별번호 검색 제공 여부, 중간 포함 검색(`/v1/ingredient/search`, PRO+ 전용으로 문서화됨)의 사용 여부. 매핑 데이터 보완은 이 단계에서 필요하지 않아 도입하지 않았다.

**성분명 자동완성**

- 앞뒤 공백 제거 후 2글자 이상 입력하면 검색창 아래에 선택 가능한 자동완성 드롭다운을 표시한다. 한글·영문 입력 모두 지원하며, 예를 들어 ‘에탄’ 입력 시 데이터에 등록된 ‘에탄올’을 후보로 표시한다.
- 후보는 한글명과 영문 INCI명을 함께 표시한다. 한글명이 없으면 영문명만 표시하며 한글명을 만들어내지 않는다.
- 정확히 일치하는 후보 → 입력어로 시작하는 후보 → 입력어가 포함된 후보 순으로 최대 10개 표시한다. 동일 성분의 여러 이름이 일치해도 후보는 성분별로 중복 제거한다.
- 마우스 클릭 또는 방향키 위·아래 이동 후 Enter로 후보를 선택하면 해당 성분이 선택되고 목록이 닫힌다. Esc 또는 검색창·후보 목록 바깥 클릭으로도 닫는다.
- 선택 후 검색어를 수정하면 기존 성분 선택을 해제한다. 후보가 없으면 ‘일치하는 성분이 없습니다’를 표시한다.
- 자동완성은 성분명 후보 검색이다. 후보 선택만으로 국가별 규제 조회를 실행하지 않으며 검색 버튼으로 별도 실행한다. 후보를 선택하지 않고 검색해도 성분 매칭을 시도하고 여러 후보이면 사용자 선택을 요청한다.

**파일로 일괄 조회**

- 다른 페이지를 거치지 않고 개발요청서 또는 성분표를 직접 업로드한다.
- 텍스트 PDF, 스캔 PDF, .xlsx, .jpg, .jpeg, .png 모두 지원한다. **현재 구현(2026-09-23)**: 텍스트 PDF(pypdf), .xlsx(openpyxl), 스캔 PDF·PNG/JPG(서버 로컬 Tesseract OCR, 한글+영문). PDF 는 쪽마다 읽힌 글자 수를 보고 20자 미만인 쪽에만 OCR 을 적용해 한 쪽을 두 번 읽지 않는다. OCR 로 읽은 행은 모두 ‘확인 필요(OCR)’로 표시하며 인식 오류를 임의 확정하지 않는다. **표 복원(2026-09-23 보완)**: 괘선(테두리)이 있는 표에서 Tesseract 가 제목 행·일부 행을 깨뜨리던 문제를 위해 (1) 회색조·괘선 제거·확대 전처리, (2) 단어 위치(image_to_data)로 줄과 셀을 복원하고 제목 셀의 x 범위로 열을 배정, (3) 제목 변형(성분명·한글/영문 성분명·INCI Name·원료명 등, 대소문자·공백·줄바꿈·끝 구두점 정규화, 한글 음절 사이 공백 제거) 처리, (4) 같은 행의 한글명·영문명은 한 성분(`name_raw`·`inci_raw`)으로, 행 번호 열이 있을 때 번호 없는 줄은 앞 행의 두 줄 셀로 병합, (5) 합계·문서 정보·결재란 행 제외, (6) 제목을 못 찾으면 어떤 줄도 성분으로 등록하지 않고 ‘표 구조 인식 실패’로 안내(글자 인식 실패와 구분), (7) 셀 신뢰도가 낮거나 글자가 깨진 행은 ‘인식 신뢰도 낮음’ 사유를 붙인다. 첫 인식(psm 6)에서 제목을 못 찾으면 psm 4 로 한 번 더 시도한다. OCR 이 준비되지 않은 서버에서는 이미지·스캔 전용 PDF 에 설치 안내(503)를 돌려주고, 혼합 PDF 는 텍스트 쪽만 처리한 뒤 읽지 않은 쪽을 표시한다. 외부 AI/OCR 서비스 전송은 없다.
- 파일 유형에 맞게 텍스트·표 추출 또는 OCR/이미지 인식을 수행한다. Excel에 여러 시트가 있으면 분석할 시트를 사용자가 선택한다.
- 규제 조회에 필요한 시장, 요청 성분명, 함량과 기준, 제품 유형·사용 조건만 추출한다. 확인·수정 후 규제 조회를 실행한다. **현재 구현**: 성분명·함량(문서에 있을 때만, 원문 그대로)·문서 비고·원문 위치를 추출하고, 문서에 적힌 국가와 제품 유형·사용 조건은 라벨 행이 있을 때 원문 텍스트로만 표시한다(시장 자동 선택 없음). 성분 구분·함량 기준 열은 이번 단계에서 두지 않는다.
- 명확한 문서 시장을 자동 선택하고 사용자가 변경할 수 있게 한다. 미기재·모호함·미지원 시장은 임의 대체하지 않는다.
- 추출·수정 정보를 유지하여 파일을 다시 업로드하지 않고 시장을 바꿔 다시 조회한다.

추출 결과 확인 화면에서 성분·함량·기준·구분·제품 조건과 시장을 수정할 수 있다. 판독 불가 항목은 직접 입력하거나 재업로드할 수 있다. 사용 제외 성분은 별도 목록으로 보이며 기본 조회 대상에서 제외한다. 선택 성분도 요청 성분임을 유지하고 실제 조회 포함 여부를 확인할 수 있게 한다.

**이번 단계 제한값 (2026-09-23 확정, `regulatory_extract.py`·`regulatory_ocr.py` 상수)**: 파일 1개 · 10 MB 이하 · PDF 20쪽 이하 · Excel 시트 20개 이하, 시트당 앞 2,000행 스캔 · 성분 행 최대 200개(초과분은 잘라내고 안내). **OCR**: 파일당 최대 10쪽, 쪽당 25초, 파일당 총 90초, 이미지 3,000만 화소(약 5,500×5,500) 초과 거부, 긴 변 2,600px 초과는 축소해 인식, PDF 쪽은 약 200 dpi 로 렌더링. 업로드 영역과 오류 메시지에 같은 값을 안내한다. 시트 선택: 시트가 2개 이상이면 서버가 시트 목록만 돌려주고, 사용자가 고른 뒤 같은 파일을 시트명과 함께 다시 보낸다(서버에 파일을 남기지 않기 위함).

## 7. 처리 과정

**직접 검색 흐름**

1. 검색 입력의 앞뒤 공백을 제거하고 영문 대소문자를 구분하지 않는 검색값을 사용한다. 원래 표시명은 보존한다. 입력이 바뀌면 기존 선택 성분과 이전 후보 요청의 유효성을 해제한다.
2. 2글자 이상이고 입력이 멈춘 뒤 약 300ms 후 성분명 후보를 조회한다. 한글 조합 중에는 요청을 보내지 않고, 조합 완료 후 길이 조건과 대기 시간을 적용한다. 2글자 미만이면 후보 요청을 하지 않고 목록을 닫는다. (2026-09-23 변경) API 문서가 검색어 최소 2글자를 요구하므로 서버 Route도 2글자 미만을 검증 오류로 돌려주며, 직접 검색 버튼도 같은 조건을 따른다.
3. `/api/regulatory/search` 로 식약처 성분 DB·규제 DB 를 한글명·영문명·이명·고시원료명·CAS 로 검색한다(정확 → 앞부분 → 포함 일치). 두 출처 후보는 합치지 않고 출처 배지(성분정보·규제정보)와 일치 근거를 붙여 최대 10개를 표시한다. 등록되지 않은 후보는 생성하지 않는다. (2026-11 변경 — 이전 K뷰티 API 의 한글/영문 시작 일치 검색을 대체)
4. 현재 검색어에 대응하는 최신 응답만 목록에 반영한다. 이전 검색어의 늦은 응답을 무시하며, 선택·Esc·바깥 클릭으로 닫힌 목록이 진행 중 응답으로 다시 열리지 않게 한다.
5. 클릭 또는 방향키 위·아래와 Enter로 후보를 선택하고 목록을 닫는다. 후보 선택용 Enter는 폼 제출·규제 조회로 이어지지 않는다. 선택한 성분과 표시 검색어를 연결해 유지하되 입력 수정 시 선택을 해제한다.
6. 사용자가 검색 버튼을 누르면 국가/시장과 성분명 입력을 검증한다. 후보를 선택하지 않았으면 후보 목록만 열고 직접 선택을 안내한다. **후보가 하나이거나 정확 일치가 하나여도 자동 선택·자동 조회하지 않는다.** 선택한 뒤 검색 버튼으로 규제 조회를 실행한다.
7. 서버가 검증한 후보 key(`/api/regulatory/lookup?key=&country=`)와 선택 시장으로 규제 DB 를 조회한다. 브라우저는 이름·CAS 를 보내지 않는다. 수집본이 바뀐 key(`stale_key`)는 선택을 해제하고 다시 검색하도록 안내한다. 자동완성 요청이나 후보 선택 자체는 규제 조회를 발생시키지 않는다.
8. 조회 상태(규제 정보 조회됨 / 선택 국가 기록 없음 / 성분 연결 확인 필요 / 규제 성분 연결 미확인 / 오류 — DB 이용 불가·후보 다시 선택 필요는 따로)와 규제 유형·규제 조건 원문을 표시한다. 직접 검색에서는 기준 비교·검토 상태를 표시하지 않으며 제품 적합성·안전성을 판정하지 않는다.

**파일 흐름: 업로드 → 추출 정보 확인 → 규제 조회 → 결과**

1. 파일 형식·실제 읽기 가능 여부와 확정된 제한을 서버에서 검증한다. (구현: 확장자 + 파일 서명(%PDF / zip 안 xl/workbook.xml) + 용량·쪽수·시트 수. 암호 PDF·손상 파일은 읽기 실패로 구분)
2. 텍스트 PDF는 텍스트·표를 추출하고, 스캔 PDF와 이미지는 OCR/이미지 인식을 수행한다. 읽히지 않는 부분은 추정하지 않고 표시한다. .xlsx는 시트 목록 확인 및 선택 후 해당 시트의 표를 추출한다. (구현: PDF 는 레이아웃 텍스트에서 `INCI name / Ingredient / 성분명 / 원료명` 등 **제목이 있는 표만** 읽고, 텍스트가 거의 없는 PDF 는 스캔 PDF 로 보고 미지원 안내. 표 제목이 없으면 성분을 만들지 않고 ‘추출 결과 없음’)
3. 규제 조회용 항목을 추출하고 원문 위치(확인 가능한 페이지·시트·셀 등), 원문값, 불명확한 부분을 함께 보관한다. (구현: 문장처럼 보이는 이름, 형식이 다른 함량, 빈 이름은 ‘확인 필요’와 사유로 표시. 함량 미기재는 `null`이며 0 으로 바꾸지 않는다)
4. 문서에 명시된 대상 시장을 식별한다. 단순 주소·참고 국가 등을 판매 대상이라고 임의 확정하지 않으며, 지원 시장 매핑이 명확할 때 자동 선택한다.
5. 사용자가 시장·성분·함량·기준·제품 조건·조회 포함 여부를 확인하고 수정한다. 입력이 불충분한 항목은 확인 필요 상태로 남기며, 사용자가 조회를 실행하기 전 규제 일괄 조회를 시작하지 않는다.
6. 확인된 조회 대상을 성분별로 매칭·조회한다. 한 항목의 매칭 실패나 API 오류가 나머지 조회를 중단시키지 않게 한다. **구현(2026-09-23)**: ‘성분 확인’ 버튼이 조회 포함 행의 성분명으로 기존 후보 검색 Route 를 **순차** 호출한다(같은 이름은 1회). 정확히 일치(공백·대소문자 무시)하는 후보가 하나일 때만 자동 확정하고, 여러 후보는 행의 목록에서 사용자가 선택하며, 후보가 없으면 ‘성분 확인 필요’다. 유사 이름을 임의 확정하지 않는다. 성분명을 수정하면 그 행의 매칭·조회 결과를 지운다. ‘확정 성분 규제 조회’는 확정 행만, (성분 코드, 시장)당 1회 순차 호출해 각 행에 결과를 연결한다. 호출 제한이 불명확해 병렬 호출은 하지 않으며, 429(rate_limit)가 오면 즉시 중단하고 남은 항목을 실패로 표시한다(자동 재시도 없음). 실패 행만 ‘실패 항목 재시도’로 다시 조회하고 성공 결과는 유지한다.
7. 규제 정보, 조건 비교와 미확인 이유를 결과에 표시한다. 재조회는 수정된 조건을 사용하며 이전 응답이 최신 결과를 덮어쓰지 않게 한다. **구현**: 시장·성분 목록·매칭이 바뀌면 ‘이전 조건의 결과’ 안내를 표시하고, 늦게 도착한 응답은 조회 순번으로 무시한다. 조건 비교(검토 상태)는 미구현이며 함량은 상세의 ‘문서 함량(참고)’로만 표시한다.

**국가 자동 선택 규칙**

- 시장 코드와 문서 국가의 매핑을 적용한다. 예를 들어 문서에 Singapore, Malaysia, Thailand가 대상 국가로 명시되어 있고 아세안 매핑이 적용되면 ‘아세안’을 자동 선택하고 ‘문서에 명시된 국가: 싱가포르·말레이시아·태국’을 표시한다.
- `ASEAN` 조회의 적용 규정 범위가 확인되지 않은 상태에서는 ‘아세안 시장 조회 / 적용 규정 범위 확인 필요’로 표시한다.
- `ASEAN` 조회가 아세안 공통 기준을 제공한다는 근거가 실제로 확인된 경우에만 ‘아세안 공통 기준 조회’로 표시한다.
- 개별 국가 규정의 확인 여부는 위 표시와 별도로 표시한다.
- 국가가 없거나 모호하면 미선택 상태에서 사용자 선택을 받는다. 여러 시장으로 나뉘어 하나로 확정할 수 없으면 감지된 국가를 보여주고 조회 시장을 선택받는다.
- 미지원 시장은 원문 시장과 함께 미지원 안내를 표시한다. 다른 지원 시장으로 조용히 대체하지 않는다. 사용자가 직접 다른 시장을 선택하면 원문 시장과 현재 선택의 차이를 표시한다.
- 시장 변경 시 추출·수정값은 유지하고 기존 결과는 이전 시장의 결과임을 표시하여 재조회를 요구한다. 새 시장의 결과처럼 재사용하지 않는다.

## 8. 출력 결과

**직접 검색 결과 카드**

직접 검색은 성분 하나를 조회하므로 표 대신 결과 카드 한 장으로 표시한다.

- 상단: 성분명(한글명)·영문 INCI명·조회 시장, 서비스 조회 시각.
- 조회 상태: 규제 정보 조회됨 / 규제 데이터 미확인 / 판단 보류(확인되지 않은 응답) / API 오류. ‘규제 정보 조회됨’은 허용·안전처럼 보이는 색으로 강조하지 않는다.
- 규제 유형: 응답의 `regulate_type` 원문.
- 규제 조건: `limit_condition` 원문을 카드 본문에 충분한 폭으로 표시한다. 원문이 ‘태그·라벨 : 값’ 블록으로 명확히 구분되면 언어별(English · API 제공 영문 → 한국어 · API 제공 한국어, 제목·구분선·여백으로 구분)로 배치한 뒤 적용 제품·부위·최대 농도·사용 조건·주의 문구·기타 원문으로 묶어 보여주고, (a)/(b) 같은 대응 표기와 수치·단위·기준은 원문 그대로 둔다. 하나라도 구분할 수 없으면 나누지 않고 원문 전체를 읽기 좋게 표시한다. 요약·환산·재해석·성분별 하드코딩을 하지 않는다.
- 상세 Modal: 검색어·조회 시장, 매칭 성분(code)·매칭 방식·API 레코드 갱신일, 조회 상태·응답 상태값·규제 구분·고시 성분명·규제 조건 원문 전체·단서 조항·실제 조회 범위·API 안내 문구, 출처·제공원 고지·규제 자료 갱신일·서비스 조회 시각·자체 검증일.
- 검토 상태·기준 충족 여부·입력 부족 안내는 직접 검색에 없다.
- 카드 하단 순서(2026-09-25 정리): ① 메타정보(실제 조회 범위·출처·확보 시각·갱신 안내·시각 안내) → ② 버튼 행: ‘규제 원문·출처 보기’(내부 상세 Modal, `<button>`)와 ‘식약처에서 사용제한 원료 확인’(외부 링크 `<a>`, 외부 링크 아이콘)을 같은 공통 보조 버튼(`.btn-soft`)으로 나란히 → ③ 사전검토 안내 한 문장과 작은 도움말. 별도 안내 패널·버튼 이름과 겹치는 설명 문구는 두지 않는다. 조회 상태와 무관하게(조회됨·출처에서 일치 항목 없음·미확인 모두) 표시한다. 전체 오류 카드(API 오류·접근 제한·출처 이용 불가)에는 오류 상태를 그대로 두고 ‘식약처에서 추가 확인’ 작은 텍스트 링크만 둔다.

**파일 일괄 조회 결과**

결과 상단에는 선택 국가/시장, 문서에 명시된 국가, 제품 유형·사용 조건, 실제 조회 범위, 서비스 조회 시각을 표시한다. 입력하지 않은 조건은 ‘미입력’으로 표시한다.

**요약 수치**

- 조회 대상 성분 수: 사용자가 이번 조회에 포함한 성분 항목 수. 사용 제외·조회 미포함 항목은 제외하며 매칭 실패 항목은 포함한다.
- 규제 정보가 조회된 성분 수: 해당 시장의 규제 근거가 실제 반환된 대상 항목 수. 통신 성공만으로 계산하지 않는다.
- 추가 확인이 필요한 성분 수: 규제 데이터 미확인, 매칭 실패·후보 미확정, 입력 부족, API 오류, 기준 불충족, 근거·적용 범위 부족 중 하나라도 있는 대상 항목 수.
- 각 수치는 성분 항목별로 한 번 계산한다. 규제 정보가 있어도 추가 확인이 필요할 수 있어 두 수치는 서로 배타적이지 않다. 동일 성분의 서로 다른 함량·조건 행을 임의 합산·병합하지 않는다.

**성분별 결과 표** (파일 일괄 조회)

화면에는 성분명·조회 상태·규제 유형·검토 상태·상세 보기를 중심으로 간결하게 두고, 요청 함량·규제 조건 원문·출처·오류 사유 전문은 상세 Modal에서 보여준다. 아래 열의 정보는 표 또는 상세 중 한 곳에서 확인할 수 있어야 한다. **현재 구현 표 열**: 성분명(매칭명·문서 함량 참고값 포함) · 선택 시장 · 조회 상태 · 규제 유형 · 상세. 검토 상태 열은 기준 비교 미구현으로 두지 않았다. 상세 Modal 은 직접 검색과 같은 Modal 을 공유하며 규제 조건을 영문 위·한국어 아래로 표시한다.

| 열 | 표시 내용 |
|---|---|
| 성분명 | 요청 성분명과 확정된 매칭명, 필수/선택 구분. 미확정이면 그 사실 표시 |
| 요청 함량 | 수치·단위·함량 기준 또는 q.s./미기재. 원료 투입량과 활성 성분 함량 구분 |
| 조회된 규제 정보 | 실제 반환된 규제 내용과 조회 상태. 없는 정보를 허용으로 해석하지 않음 |
| 사용 조건·함량 제한 | 제공된 적용 조건·제한(예: `limit_condition` 원문) 및 비교 가능한 기준. 미제공 항목 명시 |
| 검토 상태 | 해당 기준 충족 / 해당 기준 불충족 / 판단 보류와 이유. 제품 전체 판정이 아님 |
| 출처 | 제공된 자료명·링크 및 확인 가능한 날짜. 미제공이면 미제공 표시 |

‘조회 상태’는 규제 정보 조회됨 / 규제 데이터 미확인(시장 항목 없음) / 규제 목록 미등재 / 판단 보류 / 성분 매칭 실패 / 성분 확인 필요 / 접근 제한 / API 오류 / 미조회로 구분한다. ‘규제 데이터 미확인’은 API가 정상 응답했으나 선택 시장의 항목이 없는 경우(`not_listed_in_country`), ‘규제 목록 미등재’는 API 소스에 제한·금지 항목 자체가 없다고 안내한 경우(`not_listed`)이며 둘 다 허용·안전을 뜻하지 않는다. ‘접근 제한’은 401·403·429 응답(인증·요금제·호출 한도), ‘API 오류’는 연결·시간 초과·서버·형식 오류다. 결과 상단 요약은 조회 대상 / 규제 정보 조회됨 / 규제 데이터 미확인(+보류) / 접근 제한 / API 오류 / 성분 확인 필요 여섯 수치로 표시하며 각 행은 한 분류에만 속한다. ‘검토 상태’는 파일 일괄 조회에서 이와 별개로 표시하며 입력 정보 부족도 구체적인 사유로 표시한다. 예를 들어 규제 정보 조회됨과 함량 미기재에 따른 판단 보류는 동시에 표시할 수 있다. 직접 검색에는 검토 상태가 없다.

함량 단위·기준, 제품 유형·사용 조건, 적용 근거가 충분하고 서로 비교 가능할 때만 해당 기준과 비교한다. 단순 수치 대소 비교로 결론 내리지 않는다. `limit_condition` 등 규제 조건 원문은 원문 그대로 보존·표시하고, 원문에서 수치·조건을 해석해 비교할 때는 해석 근거를 함께 표시한다. 기준 충족 표시에는 비교한 조건과 근거를 명시한다. 근거가 부족하거나 출처를 확인할 수 없는 경우 판단 보류한다.

행의 상세보기는 공통 Modal로 제공한다. 원문/수정 입력, 매칭 정보, 조회된 세부 규제, 비교 근거·누락 정보(파일 조회), 실제 조회 범위 및 날짜를 표시한다. 규제 자료 갱신일, 서비스 조회 시각, 자체 검증일은 각각 다른 라벨로 표시하며 ‘확인일’ 하나로 합치지 않는다. 자체 검증을 하지 않았으면 ‘미실시’, 제공되지 않은 출처·갱신일은 ‘미제공’으로 표시한다.

성분 데이터가 전혀 없으면 Empty State를 제공한다. 성분별 실패·부족 사유가 있는 경우 이를 숨기지 않는다. 전부 규제 데이터 미확인일 때는 빈 결과 안내와 확인 필요 목록을 제공하며 ‘허용’·‘안전’으로 표시하지 않는다.

**식약처 공식 조회 연결 (2026-09-25)**: 결과 표 아래 순서는 ① 조회 상태 범례(메타) → ② 버튼 행(행별 상세는 표 안 ‘상세’ 버튼이 담당하므로 ‘식약처에서 사용제한 원료 확인’ 공통 보조 버튼만 **한 번**) → ③ 사전검토 안내와 작은 도움말(직접 검색 카드와 같은 문구·구성, 별도 패널 없음). 행마다 긴 안내를 반복하지 않는다. ‘규제 정보 조회됨’이 아닌 행(미확인·미등재·성분 연결 확인 필요·판단 보류·성분 확인 필요·매칭 실패·접근 제한·API 오류·미조회)의 조회 상태 셀과 전부 미확인일 때의 확인 필요 목록 항목에는 ‘식약처에서 추가 확인’ 작은 텍스트 링크를 붙인다. 기존 상태 배지·사유 문구는 그대로 두며 API 오류를 ‘규제 없음’·‘미등재’로 바꾸지 않는다. 상세 Modal 은 공통 안내를 반복하지 않고 ‘출처 · 날짜’ 아래에 같은 보조 버튼 하나와 작은 도움말만 둔다(기존 공공데이터포털 안내 링크 `data.go.kr` 은 다른 주소이므로 유지).

## 9. API / 외부 데이터

- **현재 (2026-11-11)**: 규제 화면의 자료는 식약처 수집 DB 두 개뿐이다 (출처 선택지 없음). (1) 성분 DB ‘화장품 원료성분정보’(`MFDS_INGREDIENT_DB_PATH`, 기본 `instance/regulatory/mfds_ingredients.sqlite`) — 성분 후보 검색·자동완성·파일 성분 매칭 (2) 규제 DB ‘화장품 사용제한 원료정보’(`MFDS_DB_PATH`, 기본 `instance/regulatory/mfds_use_restriction.sqlite`) — 후보 검색과 국가별 규제 조회. 완료된 수집 실행만 읽기 전용으로 사용하고, 앱 시작·요청 때 수집하지 않는다. K-Beauty API 는 규제 화면에서 호출하지 않는다(챗봇 이전 도구만 사용). DB 오류는 ‘검색 결과 없음’·‘미등재’로 바꾸지 않는다.
- (이전 설계, 2026-09~11-09) 출처를 화면에서 선택(식약처 수집 DB / K뷰티 API)하고 성분 검색은 K뷰티 API 로 하던 방식은 2·3단계에서 식약처 DB 검색·선택으로 바뀌었고, 출처 선택 radio 와 이전 Route 는 삭제했다.
- **식약처 DB 성분 연결**: 기존 API 성분 코드는 식별자로 쓰지 않는다. 확정 성분의 한글명·영문명·CAS 로 `INGR_STD_NAME`·`INGR_ENG_NAME`(대소문자·앞뒤 공백·연속 공백만 정규화, 숫자·기호 유지)·`CAS_NO`(토큰 단위) 정확 일치를 찾는다. 이름 일치 식별자(표준명+영문명 조합)가 정확히 하나면 확정, 둘 이상이거나 CAS 만 일치하거나 CAS 가 충돌하면 ‘성분 연결 확인 필요’(후보만 표시, 자동 확정 없음). 같은 성분·시장의 조건별 레코드는 모두 보여준다. 이름을 포함만 하는 항목(염류·유도체·성분군·이명·고시원료명)은 ‘관련 항목·적용 여부 확인 필요’로 확정 규제와 분리해 표시하며, 개별 이름으로 못 찾았다고 성분군 규정이 없다고 판단하지 않는다.
- **시장 매핑(식약처 DB)**: KR→한국, EU→EU, US→미국, CN→중국, JP→일본, ASEAN→아세안 (명시적 매핑, `regulatory_mfds_lookup.MARKET_TO_COUNTRY`). 원본 ‘유럽’(54건)은 근거가 없어 EU 에 합치지 않았으며 **이번 EU 조회 범위는 원본 ‘EU’ 항목**이다. 대만·캐나다·브라질·아르헨티나는 이번 단계에서 연결하지 않았다. 화면·`/lookup` 의 국가 검증은 `regulatory_mfds_lookup.MARKET_CODES`(KR·EU·US·CN·JP·ASEAN)를 따른다.
- **식약처 결과 표시**: `REGULATE_TYPE`(금지/한도/한도/금지)과 `LIMIT_COND` 원문을 보존한다. `LIMIT_COND` 가 null 인 ‘금지’는 금지 항목으로 표시하고 ‘제한 없음’으로 해석하지 않는다. ‘한도’인데 제한사항이 비어 있으면 ‘상세 제한사항 미제공’. 단서조항은 `PROVIS_ATRCL`. 원문이 영문·한국어로 구분되면 기존 규칙대로 영문 위·한국어 아래, 아니면 원문 그대로(번역·생성 없음, 텍스트 노드로만 렌더링). 각 결과에 조회 출처와 DB 에 기록된 수집 시각을 표시하며 이는 원천 갱신일·법령 개정일이 아니다. 출처 링크는 공공데이터 안내 페이지(개별 법령 원문 아님)이며 응답에 없는 법령 URL·개정일은 만들지 않는다.
- **식약처 출처 상태**: 규제 항목 조회 성공(found) / 해당 출처에서 일치 항목 없음(not_listed, ‘출처에서 일치 항목 없음’ — 허용·안전·규제 없음 아님) / 성분 연결 확인 필요(link_required) / DB 미설치(db_missing 503) / 수집 미완료(db_incomplete 503) / DB 읽기 오류(db_error 503). DB 문제는 ‘출처 이용 불가’로 표시하고 미등재로 표시하지 않는다. 화면(`/lookup`)의 상태는 found / no_market_record / link_required / not_linked 이며, 수집본이 바뀐 후보 key 는 stale_key(409)·not_found(404) ‘후보 다시 선택 필요’로 따로 표시한다.
- 자동완성용 성분명 후보 검색과 국가별 규제 조회를 분리한다.
- 한글명·동의어 데이터가 부족하거나 부분·영문 검색을 지원하지 않으면 검증된 성분명 검색용 매핑 데이터로 보완하도록 설계한다. 한글·영문 검색 및 자동완성은 확정 목표이며, 보완 데이터의 출처·이용 조건·검증·갱신 방식은 구현 시 확정한다. 매핑 데이터를 `src/02_regulatory/` 안에 둘 경우 공개 가능한 자료만 포함한다.
- 파일 정보 추출 도구와 규제 데이터 조회는 별도 단계·의존성으로 설계한다. AI를 사용하더라도 문서 정보 추출에 활용하며 규제 근거가 없는 판정을 생성하지 않는다.
- 규제 정보 자체 DB는 확정 범위가 아니다. 미국 등 부족한 시장 정보의 보완 필요성, 구축 여부, 데이터 출처·검증·갱신 담당 및 범위는 API 확인 후 결정한다. 이는 성분명 검색을 위한 매핑 데이터 보완과 별개이며 성분명 매핑을 규제 근거로 사용하지 않는다.

> **과거 기록 (2026-09-23 ~ 11-11)**: 초기에는 성분 검색·규제 조회에 K-Beauty Cosmetic Ingredients API(RapidAPI)를 썼고, 2·3단계에서 식약처 DB 검색·선택으로, 4-1·4-2단계에서 규제 화면 이전 경로와 챗봇을 전환했다. 4-3단계(2026-11-11)에 API 모듈(`regulatory_service.py`)·응답 기록(`test_data/`)·관련 테스트와 인증·호출·응답 처리 설명을 삭제했다. 현재 규제 기능은 외부 API 를 호출하지 않는다.

## 10. 데이터 처리

**추출·정규화 규칙**

- 직접 검색은 입력 앞뒤 공백을 제거하고 영문 대소문자를 무시해 매칭한다. 한글명·영문 INCI명·검증된 동의어를 동일 성분 식별에 연결하되 원문 입력·표시명과 검색용 정규화 값을 구분한다.
- 매핑 데이터의 출처·검증 근거를 관리하며 AI 번역만으로 동일 성분을 확정하지 않는다. 이름이 비슷하거나 여러 성분에 연결되면 사용자 확인을 받는다. 후보 목록에 표시되었다는 사실은 규제 정보가 존재하거나 기준을 충족한다는 의미가 아니다.
- 요청 성분과 사용 제외 성분을 분리한다. 바이어의 제외 요청을 법적 금지로 표시하지 않는다.
- 필수 성분과 선택 성분을 구분하며 불명확한 경우 확인을 받는다. 사용 제외 성분을 처방 구성 성분 수에 포함하지 않는다.
- 원료 투입량과 활성 성분 함량을 구분한다. 농도·순도·환산 근거가 없으면 활성 함량으로 임의 환산하지 않는다.
- 단위와 함량 기준을 원문대로 유지한다. 비교를 위한 환산은 근거가 충분하고 기준이 일치하는 경우에만 수행하며 원문과 환산 근거를 함께 표시한다.
- q.s., 함량 미기재, 향료 상세 조성 미제공은 정보 부족이다. 이를 0 또는 제한 없음으로 해석하지 않으며 향료 세부 성분을 만들어내지 않는다.
- 문서에 없는 성분·함량·조건은 생성하지 않는다. 부분 개발요청서의 합계를 100%로 맞추거나 완성 처방으로 취급하지 않는다.
- 원문값, 추출값, 사용자 수정값과 매칭값을 구분한다. 후보가 모호하면 사용자가 확인하기 전 확정하지 않는다.
- 파일 추출값과 실제 규제 근거를 구분한다. 문서 자체에 기재된 ‘허용’ 등 표현을 공식 규제 조회 결과로 사용하지 않는다.

**보관·보안·운영 요구사항**

- 시장을 바꿔 재조회할 수 있도록 현재 작업의 확인·수정된 추출 정보를 유지한다. 영구 보관을 기본 전제로 하지 않는다.
- 업로드 원본과 임시 처리 파일은 `src/` 등 공개 자산 경로에 두지 않고 다른 사용자 작업과 분리한다. 확장자만으로 신뢰하지 않고 실제 형식·파싱 가능 여부를 검증한다.
- 처리가 끝나거나 실패한 임시 파일을 정리하는 삭제 절차를 마련한다. 원본 보관 기간, 추출값 유지 기간, 만료·작업 종료 시점, 실패 시 삭제 재시도 방식은 구현 시 확정한다. 미확정 상태에서 ‘즉시 삭제’ 등으로 안내하지 않는다.
- 외부 AI/OCR 서비스 사용 여부를 확정하고, 사용 시 전송 대상·목적·보관 및 삭제 정책·사용자 안내와 동의 필요 여부를 구현 전에 결정한다. 전송 전에 확정된 방침을 안내하며 미확정 상태에서 외부 미전송을 보장하지 않는다.
- API Key·요청 헤더 값은 코드, 문서, `samples/`·`tests/fixtures/`, 브라우저 응답, 로그에 남기지 않는다. 로그에는 원문 전체·민감한 처방 정보도 불필요하게 남기지 않는다. 구체적인 로그 저장 위치·접근 통제·보관 정책은 구현 시 확정한다.
- 자료 갱신일은 제공원 메타데이터, 서비스 조회 시각은 실제 호출 시각, 자체 검증일은 실제 별도 검증 기록으로 관리한다. 한 날짜를 다른 의미로 복사하거나 누락 날짜를 생성하지 않는다. 식약처 DB 의 ‘수집 시각’은 DB `runs.finished_at` 이며 별도 라벨로만 표시한다.
- **상세 Modal 정보 배치 정리 (2026-09-26)**: 직접 검색·파일 일괄 조회가 공유하는 성분 상세 Modal 을 공통 디자인 기준으로 재배치했다(표시 방식만 변경, API 호출·매칭·규제 판정 로직 변경 없음). 기본 펼침: ① 한국어 성분명·영문명 / 선택 시장 · 조회 상태 배지(조회됨은 중립 배지, ‘사용 허용·적합 판정이 아니에요’ 문구 동반) · 규제 구분 / 문서 함량(참고, 파일 조회만) / 미조회·오류 사유 → ② ‘주요 규제 조건’: 언어별 큰 덩어리 대신 항목별(① 적용 제품·부위 ② 최대 농도 ③ 사용 조건·주의 문구, 분류 불확실은 ‘제한사항’)로 묶고 항목 안에서 영문 원문 위·한국어 제공 내용 아래. 기존 `parseConditionText` 구조화 로직 재사용(블록 경계에 줄바꿈 없이 이어지는 ‘ * 【태그】’ 를 추가 인식해 머리글이 앞 값에 섞이지 않게 함), 번역·요약 없음, (a)(b) 대응·수치·단위·RE·경고 문구 보존, ‘【Restrictions】/【제한】’ 머리글과 항목 제목과 겹치는 라벨만 생략 → ③ 관련 항목은 ‘관련 항목 N건 · 적용 여부 확인 필요’ 건수는 항상, 목록은 접힘. 식약처 성분 연결 후보(link_required)는 접지 않고 표시. 기본 접힘(접근 가능한 details/summary, 화살표 + ‘펼치기/접기’ 글자): ‘입력·매칭 근거’(검색어·시장·매칭 성분 code·매칭 방식·성분 연결 근거·성분 레코드 updated_at(규제 자료 갱신일 아님 설명 유지)·원문 위치 — 결과 표 열로는 두지 않음) / ‘전체 원문·고시 정보’(고시 성분명·규제 조건 전체 원문·단서 조항·API 안내 문구·응답 상태값·실제 조회 범위 — 등재 시장 목록은 ‘K뷰티 API 에 등재된 시장’ / ‘식약처 DB 에 레코드가 있는 국가’로 출처를 구분) / ‘출처·날짜 상세’(출처 설명은 공공데이터 안내 URL 을 링크 하나로만, 개별 법령 원문 링크 아님 명시 · 제공원 고지 · 갱신 방식 · 수집 시각은 확보 시각과 같은 수집 완료 기록이면 표시하지 않고 다를 때만 별도 · 수집 실행 정보(식약처) · 원천 자료 갱신일·법령 개정·적용일 미제공 · 서비스 조회 시각 · 자체 검증일 미실시). 하단에는 규제 조회 출처·데이터 확보 시각·‘확보 시각은 법령 개정일이나 최신성 보장을 뜻하지 않아요’ 를 항상 짧게 두고, 사전검토 안내 한 문장과 도움말, 하단 버튼은 식약처 공식 조회(`.btn-soft`, 새 탭, `noopener noreferrer`, 외부 링크 아이콘)와 닫기. 상세 안에 상세를 다시 여는 버튼은 없다. 정의 목록은 데스크톱 2열(짧은 식별정보)·1열(긴 원문), 640px 이하 1열, 긴 화학명·원문은 `overflow-wrap`·`pre-wrap` 으로 가로 넘침 없이 줄바꿈. 접근성: 열 때 닫기 버튼으로 포커스 이동·스크롤 맨 위·펼침 상태 초기화(다른 성분을 열어도 이전 상태가 남지 않음), Tab 순환, Esc 닫기(공통), 닫은 뒤 연 버튼으로 포커스 복귀(`regulatory.js` 상세 Modal 접근성 보완). 직접 검색 카드 본문의 규제 조건도 같은 렌더러를 쓰므로 같은 항목별 배치가 적용된다. 검증(2026-09-26, headless Chrome + 캐시 응답 로컬 서버, 외부 호출 0회): 직접 검색·일괄 조회 × 식약처·K뷰티 × 조회됨·미등재·미확인·성분 연결 확인 필요·API 오류 화면, 수정 전후 원문 동일(전체 원문 = 응답 `limit_condition`), 수치·단위·(a)(b)·경고 문구 보존, 포커스·Tab·Esc·복귀, 390px 폭 가로 넘침 없음 — 50개 항목 통과. **미검증**: 실제 화면 크기별 시각 확인과 스크린리더 읽기 순서는 담당자 브라우저 확인 필요.
- **식약처 공식 조회 링크 동작 (2026-09-25)**: 주소는 `https://nedrug.mfds.go.kr/pbp/CCBDF01` 하나이며 실제 `<a>` 로 `target="_blank"`·`rel="noopener noreferrer"` 를 적용해 새 탭에서 연다. 검색어 자동 전달 방식이 확인되지 않아 URL 에 쿼리 파라미터를 붙이지 않고, 버튼은 공식 조회 페이지로 이동할 뿐 해당 성분 상세 페이지로 바로 연결되는 것처럼 표현하지 않는다(도움말: 공식 페이지에서 성분명·영문명·CAS 번호로 직접 검색). 링크 이동은 JS 상태를 건드리지 않으므로 입력값·업로드 결과·선택한 시장·출처·상세 Modal 상태가 유지된다. 외부 링크 아이콘(`aria-hidden`)과 보조기기용 ‘(새 탭에서 열림)’ 문구(`regulatory-sr-only`)를 함께 둔다. 기존 API 호출·성분 검색·매칭·OCR·규제 판단 로직은 변경하지 않았다.
- **출처 선택 UI (2026-09-24, 과거 기록 — 2·3단계에서 제거)**: 당시 직접 검색·파일 탭에 ‘규제 정보 출처’ radio 카드 2개(식약처 수집 DB / K뷰티 API)가 있었다. 현재 화면에는 출처 선택지가 없고 식약처 수집 DB 만 쓴다.
- **발표 시연 자료 (2026-09-25)**: `samples/` 바로 아래에 최종 3개만 둔다(같은 날 `samples/demo/` 하위 폴더를 없애고 이동) — 영어 염모제 개발요청서 PDF(KR·EU·CN·ASEAN), 한국어 두피샴푸 주요 검토 성분표 XLSX(한국·EU·중국·아세안), 영어 선 에센스 주요 검토 성분표 PNG(KR·EU·CN·JP·ASEAN). 성분은 실제 검색·매칭·6시장×2출처 규제 조회로 검증해 선정했고(추천 시장은 두 출처 각각 90% 이상), 파일별·시장별·출처별 성공 건수, 수동 처리(살리실릭애씨드 식약처 `link_required`), 미검증 항목은 `demo_verification.md` 에 기록했다. 회귀 테스트 픽스처(`sample_*`·`eu_ser_041_development_brief.pdf`)는 `tests/fixtures/` 로 이동해 유지하고, 추출 성공 여부만 확인하던 `sample_ingredients_kr.xlsx` 는 한국어 두피샴푸 XLSX 로 참조를 바꾼 뒤 삭제. 시장 표기는 조회 시연 추천이며 수출 적합성 인증이 아니다.
- **출처별 날짜·갱신 안내 (2026-09-23)**: 결과 카드·일괄 결과 상단·상세 Modal 에 ‘데이터 확보 시각 / 갱신 안내 / 원천 자료 갱신일 / 법령 개정·적용일’을 구분해 표시한다. 시간은 KST 로 통일한다(시간대 정보가 없는 값은 변환하지 않고 ‘시간대 미표기’). (1) K뷰티 API: 확보 시각 = 서버가 외부 API 응답을 받은 시각(`acquired_at` = `queried_at`)이며, 화면은 응답에 담긴 값을 그대로 쓰므로 이전 결과를 다시 볼 때도 현재 시각이 아니라 원래 확보 시각이 보인다. 갱신 안내는 ‘월 1회 (제공자 안내 기준)’ — 근거는 제공자 공개 저장소 README 의 “Update Frequency | Monthly”(2026-09-23 확인)이며, 마지막 갱신일·스냅샷 날짜는 문서·응답 어디에도 없어 ‘미제공’으로 두고 역산하지 않는다. (2) 식약처 DB: 확보 시각 = 조회에 쓰는 완료된 수집 실행의 `runs.finished_at`(수집 완료 시각). 파일 수정 시각·현재 시각을 쓰지 않으며, 재수집이 실패하면 이전 완료 실행이 그대로 쓰여 이전 수집 시각이 유지된다. 값이 없으면 ‘수집 시각 미기록’. 자동 갱신이 없으므로 갱신 안내는 ‘수동 재수집 (자동 갱신 없음)’. (3) 두 출처 모두 원천 자료 갱신일·법령 개정·적용일은 ‘미제공’이며, 공공데이터포털 소개 페이지의 수정일을 갱신일로 쓰지 않는다. (4) 안내 문구 ‘데이터 확보·수집 시각은 법령 개정일이나 최신성 보장을 의미하지 않습니다.’를 함께 표시하고, 시각만으로 출처 간 최신성을 판정하지 않는다. 일괄 결과는 상단에 공통 정보(출처·확보 시각 범위·갱신 안내)를 한 번 표시하고, 행마다 확보 시각이 다르면 범위로 보여주며 개별 시각은 상세에서 확인한다.

## 11. 예외 처리

| 상황 | 표시 및 복구 동작 |
|---|---|
| 검색어·시장 미입력 | 해당 폼에 오류 안내. 입력 전 조회 실행 방지 |
| 자동완성 입력 2글자 미만·한글 조합 중 | 후보 요청하지 않음. 2글자 미만에서는 목록 닫기, 조합 완료 후 약 300ms 대기하여 조건 재확인. 서버 Route는 2글자 미만을 검증 오류(400)로 응답 |
| 자동완성 후보 없음 | ‘일치하는 성분이 없습니다’ 표시. 규제 데이터 미확인과 구분하고 입력 수정 안내 |
| 성분명 후보 검색 실패 | 후보 검색 실패와 재시도 안내. 후보 없음으로 표시하지 않고 입력 유지. 규제 조회 API 오류와 별도로 표시 |
| 후보 미선택 상태에서 검색 | 현재 입력으로 매칭 시도. 여러 후보이면 사용자 선택 요청, 매칭 실패이면 수정 안내. 임의의 첫 후보로 규제 조회 금지 |
| 후보 선택 후 검색어 수정 | 기존 성분 선택 해제, 수정된 입력으로 후보 재검색. 이전 선택 성분으로 규제 조회 금지 |
| 이전 후보 요청의 늦은 응답 | 현재 목록을 덮어쓰지 않음. 이미 닫힌 목록을 재개방하지 않음 |
| 흐름 점검 보완 (2026-09-23) | 직접 검색과 파일 일괄 조회는 결과 영역·상세 Modal 을 공유하므로 (1) 일괄 결과가 보일 때 직접 검색의 ‘이전 조건’ 안내를 끄고, (2) 직접 검색 카드의 ‘규제 원문·출처 보기’는 열기 직전에 마지막 직접 검색 결과로 Modal 을 다시 채운다. (3) 새 파일 추출을 시작하면 이전 파일의 성분 확인·규제 조회를 중단하고 플래그·버튼·일괄 결과를 정리하며, 추출이 실패하면 이전 확인 표(수정 내용 포함)를 되살린다. (4) 일괄 조회의 ‘이전 조건’ 판정 키는 조회 시작 시점 기준이라 조회 중에 행을 고치면 완료 후 안내가 뜬다. (5) 자동완성 목록이 다른 검색어의 것이면 검색 버튼은 후보를 다시 검색한다. (6) 성분 확인 처리 중 예외가 나도 버튼이 ‘확인 중’에 고정되지 않는다. (7) 직접 검색 오류 카드는 입력 확인·연결 실패·접근 제한·API 오류를 구분해 표시한다 |
| 지원하지 않는 문서 시장 | 원문 국가와 미지원 표시. 사용자 선택 없이 다른 시장 대체 금지 |
| 미지원 파일·제한 초과 | 업로드 오류와 허용 형식·확정된 제한 안내. 파일 교체 유도 (구현: 이미지·.xls·.csv 등은 415 `unsupported`, 10 MB·20쪽·20시트 초과는 400 `limit`. 화면은 업로드 전에도 같은 안내) |
| 손상·암호화 등 읽기 실패 | 읽을 수 없는 이유와 재업로드·직접 입력 안내. 규제 데이터 미확인과 구분 (구현: 422 `unreadable`) |
| OCR 오인식·불명확한 표 | 해당 항목을 확인 필요로 표시. 확정값 생성 금지, 수정 또는 재업로드 제공 (구현: OCR 로 읽은 모든 행을 ‘확인 필요(OCR)’로 표시. 글자 인식 실패는 ‘이미지에서 글자를 인식하지 못했어요’, 글자는 읽었으나 제목을 못 찾으면 ‘성분 표 구조를 찾지 못했어요’ + 인식된 줄 예시(`ocr.outcome` = no_text / no_header), 시간 초과·처리 실패는 422 `ocr_timeout`/`ocr_failed`, 엔진 미설치는 503 `ocr_unavailable` + 설치 안내) |
| 일부 페이지·시트 추출 실패 | 성공 범위와 미처리 범위를 명시하고 확인·수정 가능. 문서 전체 추출 완료로 표시 금지 |
| 성분 미검출·빈 시트 | 추출 Empty State와 시트 재선택·재업로드·직접 입력 안내 (구현: `status = empty`, 표는 비어 있고 ‘행 추가’로 직접 입력 가능) |
| 성분 매칭 실패 | 실패 상태 및 성분명 수정 안내. 규제 데이터 미확인과 구분 (구현: 확인 표 ‘성분 확인 필요’, 결과 표 ‘성분 매칭 실패’. 조회하지 않음) |
| 여러 매칭 후보 | 후보 확인 전 성분 확인 필요 상태. 해당 항목을 임의 확정하지 않고 나머지 결과는 제공 (구현: 행의 후보 목록에서 선택. 미확정 행은 결과 표에 ‘성분 확인 필요’로 남고 조회하지 않음) |
| 함량·기준·조건 부족 (파일 조회) | 구체적인 누락 항목 표시. 규제 정보 조회는 가능하되 기준 비교는 판단 보류. 직접 검색에는 해당 없음 |
| 규제 DB 에 선택 시장 기록 없음(`no_market_record`)·연결되는 규제 성분 없음(`not_linked`) | ‘선택 국가 기록 없음’·‘규제 성분 연결 미확인’과 추가 확인 필요 표시. 허용·안전 판단 금지 (이전 K뷰티 API 의 `data=[]`·`not_listed_in_country` ‘규제 데이터 미확인’ 대체) |
| 확인하지 않은 `result_status` 값·예상과 다른 응답 구조 | 임의 해석 금지. 판단 보류·추가 확인 필요로 표시 |
| 식약처 DB 미설치·수집 미완료·읽기 오류 (`db_missing`·`db_incomplete`·`db_error` 503) | ‘출처 이용 불가’ 표시(성분정보·규제정보 구분). 검색 결과 없음·미등재로 변환 금지. 파일 일괄 조회는 그 자리에서 중단하고 남은 행은 같은 이유로 미조회 |
| 연결 실패·응답 해석 실패 등 그 밖의 요청 오류 | 오류 표시, 민감정보 없는 사유와 재시도 안내. 규제 데이터 미확인으로 변환 금지 |
| 일부 성분 조회 실패 | 성공 결과 유지, 실패 항목과 건수 표시 및 해당 항목 재시도 제공 |
| 전체 조회 실패 | 공통 Error State와 재시도. 확인한 입력은 유지 |
| 재조회 또는 입력 변경 | 이전 조건의 결과임을 명시하고 재조회 요구. 오래된 응답이 새 조건 결과를 덮어쓰지 않음 |

처리 중 ‘업로드 중’, ‘시트 확인 중’, ‘텍스트·표 추출 중’, ‘문자 인식 중’, ‘규제 조회 중’ 등 실제 단계에 맞는 상태를 표시한다. 측정할 수 없는 진행률은 만들지 않는다. 실행 버튼은 로딩·disabled로 중복 실행을 막고 서버에서도 중복 처리 방식을 마련한다. 종료·오류 후에는 복구 가능한 동작을 다시 활성화한다.

- **상세 Modal 위치 (2026-09-23, PM 공유 사항)**: 공통 `main.container` 에 `container-type: inline-size` 와 진입 애니메이션(`transform`)이 있어 그 안의 `position: fixed` Modal 은 뷰포트가 아니라 컨테이너 기준으로 배치된다(긴 페이지에서 배경만 보이고 창은 화면 밖). 담당 JS 가 페이지 로드 시 `#regulatory-detail-modal` 을 `body` 바로 아래로 옮겨 해결했다. 공통 `common.js` 는 id 로 찾으므로 동작은 같다. 같은 구조의 다른 페이지 Modal 도 영향을 받을 수 있어 PM 에게 공유한다.
- 공통 UI 문서의 Table 설명은 Header 14px·배경 없음이나 실제 CSS는 `--font-size-caption`·`--color-surface-muted`를 사용한다. 페이지 CSS로 덮어쓰지 않고 PM이 규격과 구현의 정합성을 확정해야 한다.
- 공통 CSS의 Shape 주석은 Card 그림자 없음으로 되어 있으나 디자인 문서와 실제 `.card`는 `--shadow-card`를 사용한다. 주석 정합성은 PM 확인 사항이다.

- 추출값 편집 표·시트 선택·단계 표시 등은 기존 Form·Table·Alert 조합을 우선한다. 별도의 공통 컴포넌트가 필요하면 규격을 새로 정의하지 말고 PM과 협의한다.

## 13. Flask / app.py 연동

- 기존 프로젝트 구조에 맞춰 구현한다. 긴 처리 로직(외부 API 호출, 파일 추출, 매칭·비교)은 `src/02_regulatory/` 내부 Python 모듈에 두고, `app.py`에는 Route와 필요한 연결 코드(import 등)만 둔다. Blueprint나 별도 실행 파일은 필수 구조가 아니다.
- `app.py`는 하단 `[B] 국가별 인허가 규제` 영역에 필요한 Backend Route와 연결 코드를 추가할 수 있다. 기존 Route와 다른 담당자 영역은 변경하지 않는다.
- 새 API URL은 `/api/regulatory/` 접두사, 새 Flask 함수명(endpoint)은 `regulatory_` 접두사를 사용한다. 기존 페이지 URL `/regulatory`와 endpoint `regulatory`는 유지한다.
- 서버가 파일 추출 도구 및 규제 API를 호출한다. 브라우저가 비밀 Key를 보유하거나 외부 규제 API를 직접 호출하지 않게 한다.
- 페이지 JS는 IIFE 또는 `DOMContentLoaded` 안에 작성하여 전역 변수 충돌을 방지한다. 공통 탭·Modal 동작은 재구현하지 않는다.
- 요청 검증·오류 구분·부분 성공 응답 계약과 처리 상태 전달 방식은 구현 시 확정하여 `api_reference.md`에 기록한다.

**환경변수**

- 규제 화면(메인 서버)은 DB 경로 `MFDS_DB_PATH`(규제 DB)·`MFDS_INGREDIENT_DB_PATH`(성분 DB)만 읽는다(둘 다 선택, 비우면 `instance/regulatory/` 기본 경로). `app.py`의 기존 `load_dotenv()`로 로드된 값을 `os.getenv()`로 읽는다.
- `MFDS_API_KEY` 는 별도 수집 스크립트(`mfds_use_restriction.py`·`mfds_ingredients.py`)에만 쓴다. DB 조회·서버 실행에는 필요 없다.
- K-Beauty(RapidAPI) 설정은 쓰지 않는다 (4-3단계에서 `.env.example`·문서에서 삭제). 운영 환경변수 정리는 배포 단계에서 한다.

**OCR 설치·실행 (2026-09-23)**

- 저장: `instance/regulatory/mfds_use_restriction.sqlite` (Git 제외 `instance/`, `/assets` 공개 경로 아님, 기존 서비스 DB `instance/cosmoa.db` 와 별개). 테이블 `runs`(실행 조건·시각·상태·건수·호출 수) / `pages`(쪽별 요청·응답 건수·totalCount·resultCode·HTTP·내용 해시) / `records`(원본 9개 필드 그대로 + raw_json + run·page·row). 페이지 하나가 트랜잭션이며 이미 저장된 쪽은 다시 저장하지 않는다.

- 안전장치: 첫 쪽에서 요청 페이지 크기가 실제 적용됐는지 확인(아니면 중단), 본 수집 중 페이지 크기 고정, 재개 시 페이지 크기·totalCount 변화 확인, 인증(401/403·resultCode 20/30~33)·한도(429·22) 오류는 재시도 없이 중단, 일시 오류는 제한 재시도, `resultCode≠00`·XML 오류·예상 밖 구조는 빈 데이터로 취급하지 않고 중단, 반복 페이지·조기 빈 페이지 감지, 완료 건수와 totalCount 대조. 미완료 실행은 `status` 로 구분되고 이전 완료 데이터는 유지된다.
- 해석 원칙: 같은 성분의 국가별·조건별 레코드를 합치거나 지우지 않는다. `LIMIT_COND` 가 null 인 ‘금지’ 를 ‘제한 없음’으로 보지 않는다. 미조회 성분을 허용·안전·규제 없음으로 판단하지 않는다. 수집 시각은 원천 갱신일·법령 개정일이 아니다. 복수 물질·CAS·이명은 원문 그대로 두고 분석 집계에서만 정규식으로 CAS 토큰을 센다.

### 17-2. 사용자 작업 흐름 [제안]

```
[프로젝트 선택] ─(공통 프로젝트 바)
      │
 ① 직접 검색 → 후보 선택 → 시장 → 조회 결과 카드
      │        └ 규제 행(entries) 옆 체크 → [확인사항 메모 작성] → 메모 편집기 (선택한 행 원문 = 읽기 전용) → [메모 저장]
 ② 파일 일괄 조회 → 결과 표에서 저장할 성분 행 체크 → [선택 항목 메모 작성] → 성분별 메모 편집 → [메모 저장]
 ③ [메모만 작성] → 성분명(직접 입력, 선택)·대상 국가(선택)·메모 → [메모 저장]
      │
 프로젝트별 메모 목록 (규제 화면 안 패널) → 상세 → 메모·대상 국가 수정 / [삭제] (요청서 반영 전만, 확인 후)
      │
 (후속, 개발요청서 담당) 요청서에서 메모 선택 → 반영 → 요청서 저장 시 서버가 메모 사본을 version_links 에 기록
```

1. 규제 조회 자체는 지금처럼 **프로젝트 없이** 할 수 있다. 메모 **저장**에만 프로젝트가 필요하다.
2. 메모 편집기를 열 때 선택돼 있던 프로젝트가 그 메모의 **연결 프로젝트**다 (요청서 연결 프로젝트 규칙과 같은 방식, `api_contract.md` 5-3·`development.md` 9-1 3번).
3. 저장 버튼은 **메모 편집기 안의 메모 단위 동작**이다. 탭 전체를 버전으로 남기는 공통 저장 영역(정식 저장·임시저장·불러오기·최종본)과 다르다 — 그 영역의 위치는 아직 합의 전이므로(`development.md` 9-1 2번) 이 기능에서 정하지 않는다.

### 17-3. 메모 1건의 단위 — 추천안

**추천 [제안]: 메모 1건 = 성분 1개 × 조회 시장 1개(또는 조회 없음).** 그 조회 결과에서 사용자가 **체크한 규제 행 0~N개**를 같은 메모에 담는다.

| 경우 | 처리 | 실제 예 (배포 규제 DB 2026-11-09 수집본) |
|---|---|---|
| 한 성분·한 시장에 규제 행 1개 | 메모 1건, 행 1개 | 페녹시에탄올 × KR — `한도`, "배합한도 : 1%" 1행 |
| 한 성분·한 시장에 규제 행 여러 개 | 메모 1건에 사용자가 고른 행만. 기본은 전체 체크가 아니라 **사용자가 직접 체크** | 1-나프톨 × KR — `한도/금지` 2행. 같은 성분·시장 조합이 2행 이상인 경우는 6개 시장에서 약 155건 (성분 구분값·국가 기준 집계) |
| 한 행 안에 여러 용도 조건 | 행 단위로만 고른다. **행의 일부 문장만 잘라 원문으로 저장하지 않는다** (잘라낸 문장은 클라이언트가 만든 문자열이 됨). 특정 용도만 해당하면 메모에 적는다 | 징크옥사이드 × KR — 한 행에 `<자외선차단제> 25%` 와 `<비타르색소>` |
| 여러 성분 (파일 일괄 조회) | 성분마다 메모 1건씩. 한 요청으로 여러 건을 함께 만든다 (17-7 `batch`) | 선크림 성분표에서 징크옥사이드·티타늄디옥사이드·페녹시에탄올 × EU 3건 |
| 여러 시장 | 시장마다 별도 조회 → 별도 메모 | 레티놀 EU(found 1행) 와 KR(no_market_record) 은 2건 |

- 근거: 개발요청서 반영(`version_links`) 단위가 메모 1건이고, R&D 전달 문구도 보통 "성분 × 시장" 으로 묶인다. 성분 여러 개를 한 메모에 넣으면 일부만 반영하거나 일부만 수정할 수 없다.
- **사용자가 보지 않은 내용은 저장하지 않는다**: 체크할 수 있는 행은 화면에 실제로 표시된 `entries` 뿐이다. 관련 항목(`related`, 적용 여부 확인 필요)·연결 후보(`link_candidates`)·다른 시장 기록은 저장 대상이 아니다 (관련 항목 첨부는 [후속]). 서버도 요청한 행이 그 key·시장 조회 결과에 있는지 확인한다 (17-6).

### 17-4. 대상 국가와 규제 조회 시장의 구분

현재 계약의 `country`(ISO 2글자, `data_contract.md` 1-5, 기본설계 `db_rules.md` 2-1 3번)는 대상 국가다. 그런데 규제 조회 시장은 `KR·EU·US·CN·JP·ASEAN` 6개이고 그중 `EU`·`ASEAN` 은 국가가 아니다. 또 규제 DB 에는 6개 시장 밖의 국가 기록(대만·브라질·아르헨티나·캐나다 등, 2026-11-09 수집본 기준 11개 국가·권역)도 있고, 바이어 국가는 더 다양하다.

**[확정 R1] — 조회 시장과 업무 대상을 분리한다** (값 이름·화면 문구는 [제안])

| 값 | 뜻 | 누가 정함 | 허용값 |
|---|---|---|---|
| `lookup_market` | 실제로 규제 DB 를 조회한 시장 (조회 근거) | **서버** (검증된 조회 요청의 시장) | `KR`·`EU`·`US`·`CN`·`JP`·`ASEAN` (CHECK, `regulatory_mfds_lookup.MARKET_CODES` 와 같음). 시장별 조회 기록에만 있다 (17-5) |
| `target_country` | 메모가 겨냥하는 업무 대상 국가 1개 | 사용자 (선택) | **유효한** ISO 3166-1 alpha-2 국가 코드 (형식 `^[A-Z]{2}$` + 서버가 국가 코드 목록으로 확인 — `EU` 같은 예약 코드·없는 코드는 거부). **6개 시장으로 제한하지 않음** |
| `target_region` | 국가가 아닌 권역 전체가 대상일 때 | 사용자 (선택) | `EU`·`ASEAN` (CHECK) |

- 메모 한 건의 대상은 `target_country` **또는** `target_region` 중 **하나**다 (CHECK `num_nonnulls(…) <= 1`). 둘 다 비면 "대상 미지정" — 허용 (기존 제안 유지).
- **여러 개별 국가가 대상이면 메모를 나눈다** (예: ASEAN 조회 결과를 VN·TH 바이어에게 각각 전달 → 메모 2건, 같은 조회를 두 번 첨부). 국가 목록 배열은 두지 않는다.
- 화면 기본값 [제안]: 조회 시장이 KR·US·CN·JP 면 `target_country` 를 같은 국가로, EU·ASEAN 이면 `target_region` 을 미리 채운다. 사용자는 회원국(예: ASEAN 조회 후 `VN`) 등으로 바꾸거나 비울 수 있다.
- **대상 국가를 바꿔도 조회 근거의 적용 국가는 바뀌지 않으며, 바뀐 것처럼 표시하지 않는다.** 예: ASEAN 조회 결과를 VN 대상으로 저장하면 화면·응답은 "규제 근거: 아세안(ASEAN) 기록 (식약처 수집 DB)" 과 "업무 대상: 베트남" 을 **다른 칸**에 보여 준다. "베트남 규제", "베트남 기준 한도" 처럼 근거를 대상 국가 이름으로 부르지 않는다 (이 문서 5장 아세안 원칙). 요청서 반영 사본(17-11)도 두 값을 따로 담는다.
- 6개 시장 밖 국가(예: 대만 `TW`)는 지금 조회 시장이 없으므로 **메모만**(또는 다른 시장 조회 + 대상 국가 TW) 으로 남긴다. 규제 DB 에 있는 대만 기록을 화면에서 조회하는 기능은 이번 범위가 아니다 [후속].

| 칸 | 담는 것 |
|---|---|
| `selection` | 사용자가 고른 후보: `source`(`mfds_ingredients`/`mfds_restriction`), `key`(참고용), `kr_name`·`eng_name`·`synonym`·`cas` 원문, `record_id`(그 수집본 안 id) |
| `regulation_identity` | 연결된 규제 성분 구분값 `std_name`·`eng_name_normalized` (규제정보 후보면 직접, 성분정보 후보면 `link`) |
| `link` | `status`(`direct`/`linked`/`none`)·`basis` |
| `market` | `code`·`country_names`(예: `["아세안"]`) |
| `entries` | **사용자가 체크한 행만**: `country`·`regulate_type`·`notice_ingr_name`·`proviso`·`limit_condition`·`limit_missing` 원문, `record_id`·`page_no` |
| `entries_available` | 그 조회에서 화면에 표시된 행 수 (예: 2행 중 1행 저장 → `1/2` 로 "일부 선택" 표시) |
| `sources.mfds_ingredients` / `sources.mfds_restriction` | **이 기록을 만들 때 실제로 사용한 DB 마다** `snapshot_id`·`run_id`·`status`·`started_at`·`collected_at`(수집 완료 시각)·`records` — 17-6 에서 검증한 바로 그 수집본. 성분정보 후보 조회·검색 0건 = 둘 다, 규제정보 후보 직접 조회 = `mfds_restriction` 만 |
| `notices` | 저장 당시 안내 원문: 출처 `disclaimer`, 상태 안내(예: no_market_record 의 "허용·안전·규제 없음을 뜻하지 않아요"), "수집 시각은 법령 개정일이 아님" |
| `search` | `search_no_result` 일 때만: 검색어 원문·정규화값·출처별 건수(`counts`, 모두 0). `selection`·`entries`·`market`·`link` 는 없음 |
| `file` | `file_batch` 일 때만: 사용자가 확인한 추출 성분명·함량 원문 문자열, 원본 파일명 (`db_rules.md` 6장 메타데이터 범위). **파일 본문·이미지·추출 원자료 전체(`raw_extracted_data`) 없음** |

- 후보 key 는 수집본 안에서만 유효하다(이 문서 9·10장, `regulatory_search` `stale_key`). 그래서 key 만 저장하지 않고 **이름·CAS 원문 + 수집본 지문 + 원문 행 사본**을 함께 남긴다. `record_id` 는 그 수집본 안에서만 의미가 있다.
- 배포 DB 를 새 수집본으로 바꿔도(`data/regulatory/README.md` 4장) 저장한 메모의 `lookup_snapshot`·`regulation_text` 는 **자동으로 바뀌지 않는다.**

### 17-6. 서버가 원문·출처를 확보하고 수집본을 검증하는 방법

클라이언트는 **규제 원문·상태·출처·성분명(시장별 조회 기록)·수집본 정보를 보내지 않는다.** 보내는 것은 "무엇을 골랐는지"(후보 key·시장·행 id 또는 검색어), **화면이 본 수집본 지문(비교용)**, 사용자 입력(메모·대상)뿐이다.

**문제 (R1 보완)**: 지금 `resolve_key` 는 **후보가 속한 DB 의 snapshot_id 만** 검사한다 (`regulatory_search.py`, 키 형식 `<source>:<snapshot_id>:<id>`). 성분정보 후보를 고른 뒤 **규제 DB 만** 새 수집본으로 바뀌면 후보 key 는 그대로 유효하지만, 저장 때 다시 조회한 규제 원문은 사용자가 화면에서 본 것과 다를 수 있다.

**원칙 [확정 R1]** (필드 이름은 [제안], 모두 **미구현** — 조회 코드는 R3 에서 바꾼다)
1. 저장할 때 **그 기록을 만드는 데 실제로 사용한 DB 마다** snapshot_id 를 검증한다.

   | 기록 | 실제 사용한 DB | 검증 대상 |
   |---|---|---|
   | `market_lookup` — 성분정보 후보 (`mfds_ingredients:…`) | 성분 DB(후보 확인) + 규제 DB(성분 연결·국가별 조회) | **성분 DB·규제 DB 둘 다** |
   | `market_lookup` — 규제정보 후보 (`mfds_restriction:…`) | 규제 DB | **규제 DB** (성분 DB 는 사용하지 않으므로 비교하지 않음) |
   | `search_no_result` | 검색한 성분 DB·규제 DB | **둘 다** |
   | `memo_only` | 없음 | 없음 |

2. 클라이언트가 보낸 예상 snapshot_id(`expected_snapshots`)는 **비교 조건으로만** 쓴다. 저장하지 않고, 저장할 원문·출처·수집본 정보(`lookup_snapshot.sources` 등)는 서버가 직접 읽어 만든다.
3. **검증한 수집본과 사본을 만든 수집본이 같아야 한다.** 비교에 쓰는 snapshot_id 와 사본(`entries`·`sources`)은 **같은 한 번의 서버 조회 결과**에서 나온다. 비교 뒤 DB 를 다시 읽어 사본을 만들지 않는다.
4. 수집본이 다르면 **저장하지 않는다** (409). 화면은 메모·대상 국가 입력을 유지하고 재조회·재선택을 안내한다 (17-8).

**조회 응답에 추가할 검증 필드 [제안, 미구현]**

| 응답 | 필드 | 내용 |
|---|---|---|
| `GET /api/regulatory/lookup` (직접 검색·파일 일괄 조회 공통) | `basis_snapshots` | 이 조회에 **실제로 사용한** DB 의 snapshot_id. 성분정보 후보 `{"mfds_ingredients": "e364…", "mfds_restriction": "a74e…"}` / 규제정보 후보 `{"mfds_restriction": "a74e…"}` |
| `GET /api/regulatory/search` | `sources.<source>.snapshot_id` (**구현됨**) + `basis_snapshots` (추가, 같은 값 모음) | 검색한 두 DB 의 snapshot_id. 검색 0건 기록에 쓴다 |

- 지금 `lookup_candidate` 응답에는 수집 시각(`selection.collected_at`·`regulation_source.collected_at`)만 있고 snapshot_id 가 없다. R3 에서 `lookup_candidate` 가 **자신이 사용한 색인의 snapshot**(후보 DB = `resolve_key` 의 snapshot, 규제 DB = `_index(SRC_RSTR)` 의 snapshot)을 결과에 담아 돌려주게 한다.
- 규제 행을 읽는 `lookup_by_identity` 는 이미 `expected_run`(run_id·시작·완료 시각)으로 색인과 같은 실행인지 확인한다. R3 에서 이 확인을 snapshot_id 기준으로 맞춰, 한 요청 안에서 파일이 바뀌어도 다른 수집본의 행이 섞이지 않게 한다.
- 챗봇은 메모를 저장하지 않으므로 이번 변경 대상이 아니다.

**저장 요청에서 받는 검증 필드**: `lookup.expected_snapshots` / `search_no_result.expected_snapshots` — 화면이 조회·검색 응답의 `basis_snapshots` 를 그대로 보낸다. 키 집합은 위 표의 "검증 대상" 과 **정확히 같아야** 한다 (빠지거나 남으면 400 `invalid_parameter`, `field: expected_snapshots`).

**서버 처리 순서 [제안]**
1. 본문 검사: 허용 필드만 받는다. 원문·출처·상태·수집본 정보(`regulation_text`, `lookup_snapshot`, `entries`, `lookup_status`, `lookup_source`, `looked_up_at`, `sources`, `collected_at`, `market_lookup` 의 `ingredient_*`)가 있으면 400 `unknown_fields` (공통 규칙 `api_contract.md` 1-1). `expected_snapshots` 는 비교 조건일 뿐 출처 입력이 아니므로 이 규칙과 충돌하지 않는다.
2. **한 번** 조회: `market_lookup` 은 `lookup_candidate(key, market)`, `search_no_result` 는 `search(query)` (읽기 전용 SQLite, 외부 호출 없음, 지금 화면 조회와 같은 함수). 결과와 `basis_snapshots` 를 함께 받는다.
   - 후보 DB 수집본이 바뀌었으면 여기서 `resolve_key` 가 `stale_key` → 409 `stale_key`.
3. 수집본 비교: 2번의 `basis_snapshots` 와 `expected_snapshots` 가 DB 마다 같아야 한다. 하나라도 다르면 409 `snapshot_changed` + `changed: [{"source": "mfds_restriction", "expected": "…", "current": "…"}]`. **성분 DB 는 그대로, 규제 DB 만 바뀐 경우가 여기서 걸린다.**
4. 선택 검사: `selected_record_ids` ⊆ 2번 결과 `entries[].record_id` (아니면 400 `invalid_selection` — 화면에 없던 행·다른 시장 행·관련 항목 차단). `found` 는 1개 이상, `no_market_record`·`not_linked` 는 빈 목록, `link_required` 는 400 `link_required`. `search_no_result` 는 2번 `total = 0` 이어야 한다 (아니면 400 `search_has_results`).
5. 사본 생성: `lookup_snapshot`·`regulation_text`·`lookup_status`·`looked_up_at`·`ingredient_*`·`lookup_source` 를 **2번 결과로만** 만든다. `lookup_snapshot.sources` 에는 3번에서 검증한 수집본(= 2번이 사용한 수집본)을 넣는다.
6. 업무 DB 트랜잭션: 프로젝트 행 확인(존재·보관) → INSERT → 커밋. SQLite 읽기는 트랜잭션 전에 끝낸다.
7. 화면·응답은 원문(`lookup_snapshot.entries`, 읽기 전용, "식약처 수집 DB 원문 · 저장 당시")과 `memo`("담당자 메모")를 **다른 영역**에 표시한다.

- 수집본이 같으면 2번 결과는 사용자가 본 결과와 같다 (같은 파일·key·시장 또는 검색어).

**batch (파일 일괄 조회)**: `{"items": [ {"lookup": {"candidate_key": …, "market": "EU", "selected_record_ids": […], "expected_snapshots": {…}}, "file": {"file_name": "sun_essence.pdf", "extracted_name": "Zinc Oxide", "amount_text": "15%"}, "target_country": …, "memo": …}, … ]}`. 항목은 `lookup` 또는 `search_no_result` 중 하나다. 각 항목을 위와 같이 서버가 재조회·검증하고 하나라도 실패하면 아무것도 만들지 않는다. 오류에 실패 항목 순번(`index`)과 코드를 담아 화면이 그 행만 표시한다.

**목록**

```json
GET /api/projects/12/regulatory-notes?limit=20
200 {"ok": true, "limit": 20, "next_before": null,
     "items": [{"id": 32, "note_type": "memo_only", "ingredient": {"name": "…", "name_source": "user"},
                "lookup_market": null, "target_country": "TW", "target_region": null, "lookup_status": null, "entries_count": 0,
                "memo_preview": "대만 바이어가 …(120자)", "collected_at": null, "revision": 1,
                "created_by": {"id": 3, "name": "…"}, "updated_by": {"id": 3, "name": "…"}, "updated_at": "…",
                "applied": false, "can_delete": true}, …]}
```
- `applied`: 개발요청서 반영 출처(`version_links.source_note_id`)로 참조되었는지. `can_delete`: 반영 전이고 삭제 주체 규칙(17-10)을 만족하는지 — 화면이 삭제 버튼 표시에 쓴다 (서버가 삭제 요청 때 다시 확인).

**수정**

```json
PATCH /api/regulatory-notes/31
{"expected_revision": 1, "memo": "…수정한 메모…", "target_country": "TH", "target_region": null}
200 {"ok": true, "note": {…, "revision": 2, "updated_by": {…}, "updated_at": "…"}}
```
- 받는 필드: `expected_revision`(필수)·`memo`·`target_country`·`target_region` 만. 그 외(`lookup`·`regulation_text`·`project_id`·`note_type` 등)는 400 `unknown_fields`.
- `memo_only` 의 메모를 빈 값으로 바꾸면 400 `empty_note` (메모만 있는 기록의 유일한 내용).
- 반영된 메모도 수정할 수 있다. 이미 저장된 요청서·반영 사본은 바뀌지 않는다 ([확정] `db_rules.md` 5-1).

**삭제**

```json
DELETE /api/regulatory-notes/31
X-CSRF-Token: …
Content-Type: application/json

{"expected_revision": 2}
200 {"ok": true, "deleted": {"id": 31, "project_id": 12}}
```
- `Common.api("DELETE", url, {expected_revision})` 로 보낸다 (CSRF 헤더·JSON 본문, 2026-11-13 확인한 `common.js` 동작).
- 서버 순서: 한 트랜잭션에서 메모 행 `FOR UPDATE` → 프로젝트 보관 확인 → `revision` 비교 → 삭제 주체 확인(17-10) → 반영 여부 확인 → `DELETE`. 반영 확인과 별개로 DB 의 `ON DELETE RESTRICT` 가 최종 보장한다 (동시에 요청서가 반영 저장하면 먼저 커밋한 쪽만 성공 — 17-10).
- 없거나 이미 지운 메모는 404 `note_not_found` (중복 삭제는 성공으로 보지 않음).

**오류**

| 상태 | `error.code` | 화면 처리 (입력은 항상 유지) |
|---|---|---|
| 400 | `missing_fields`, `unknown_fields`, `invalid_parameter`(+`field`: memo 길이·국가 코드·`expected_snapshots` 키 집합 등), `empty_note`, `invalid_selection`(행이 그 조회 결과에 없음·상태와 맞지 않는 개수), `search_has_results`, `link_required`(성분정보 후보가 규제 성분 하나로 연결되지 않음 — 연결 후보 선택 필요), `project_archived`, `invalid_json`, `json_required` | 해당 칸·행 표시 |
| 401 | `unauthorized` | 로그인 안내 |
| 403 | `csrf_failed` (`Common.api` 가 1회 재시도) / `note_delete_forbidden` (삭제 주체 아님 — 17-10 [제안]) | 재시도 / 삭제할 수 없는 이유 안내 |
| 404 | `project_not_found`, `note_not_found` | 프로젝트 다시 선택·목록 새로 고침 |

| 413 | `payload_too_large` (snapshot·batch 상한) | 잘라 저장하지 않았다고 안내 |

### 17-8. 조회 상태별 저장과 오래된 key

| 화면 상태 | 기록 유형 | 메모 저장 | 저장되는 뜻 |
|---|---|---|---|
| 조회됨 `found` | `market_lookup` | 체크한 행 1개 이상과 함께 | "식약처 수집 DB 에 이 시장 기록이 있음 (저장 당시)". 허용·적합 판정 아님 |
| 선택 국가 기록 없음 `no_market_record` | `market_lookup` | 행 없이 상태만 (`selected_record_ids: []`) + 메모 | "규제정보에 성분 기록은 있으나 선택 시장 기록 없음". 화면·사본에 **"허용·안전·규제 없음을 뜻하지 않음"** 안내 원문을 함께 저장 |
| 연결 미확인 `not_linked` | `market_lookup` | 상태만 + 메모 | "성분정보 후보와 정확히 연결되는 규제정보 항목 없음". 같은 안내 |
| 연결 후보 선택 필요 `link_required` | — | **조회 첨부 불가** (400 `link_required`). 연결 후보를 직접 고른 뒤 저장하거나 메모만 작성 | — |
| 검색 결과 없음 (두 DB 후보 0건) | `search_no_result` | 서버가 두 DB 0건 재확인 + 메모. 시장 없음 | "저장 당시 두 DB 에서 검색어와 일치하는 후보 없음". 같은 안내 |
| 식약처 DB 오류 (`db_missing` 등) | — | 조회 첨부 불가. `memo_only` 만 가능 | 오류를 '결과 없음'으로 저장하지 않는다 (이 문서 11장 원칙) |

- **[확정] 검색 결과 없음·특정 시장 기록 없음·연결 미확인을 허용·안전·규제 없음으로 표현하지 않는다.** `lookup_status`·`note_type` 와 별개로 "규제 없음"·"사용 가능"·"적합" 같은 값·열을 두지 않는다. 목록 Badge 도 화면의 기존 상태 문구(`조회됨`·`선택 국가 기록 없음`·`연결 미확인`·`검색 결과 없음`)만 쓴다.

**저장 직전에 수집본이 바뀐 경우 (배포 DB 교체 후 같은 화면에서 저장)** — 두 경우 모두 아무것도 만들지 않는다

| 응답 | 뜻 | 화면 안내 |
|---|---|---|
| 409 `stale_key` | 고른 후보가 속한 DB 가 바뀜 — 후보 key 자체가 무효 | "수집본이 바뀌어 성분을 다시 검색해야 해요" + [다시 검색] (선택했던 성분명으로 검색어 채움) |
| 409 `snapshot_changed` | 후보 key 는 유효하지만 **조회에 쓴 다른 DB 가 바뀜** (예: 성분 DB 는 그대로, 규제 DB 만 교체) · 또는 검색 0건 기록의 두 DB 중 하나가 바뀜 | "규제정보 수집본이 바뀌어 조회 결과가 달라졌을 수 있어요" + [다시 조회] (같은 후보·시장으로 재조회 — 행 id 가 바뀌므로 **행을 다시 체크**) / 검색 0건이면 [다시 검색] |

- 공통: 메모·대상 국가 입력을 **그대로 유지**하고 첨부한 조회 결과에만 표시한다. 체크했던 행은 새 결과에서 다시 고르게 하며, 이름이 같다고 자동으로 다시 체크하거나 비슷한 후보로 바꿔 저장하지 않는다.
- batch 는 전부 취소하고 바뀐 행만 표시한다.

**이미 저장한 과거 메모를 다시 볼 때**
- 저장된 `lookup_snapshot`·`regulation_text` 만으로 보여 준다. **현재 key 가 유효한지 확인하지 않고, 현재 DB 가 없거나 바뀌어도 열람은 된다.**
- 표시: "저장 당시 원문 · 규제정보 수집 완료 2026-11-09T08:55:53Z (snapshot a74e63a3…)" — 수집 시각을 법령 개정일·최신 규정으로 표현하지 않는다.
- [제안] 현재 배포 DB 의 snapshot_id 와 다르면 "현재 서버 DB 는 다른 수집본이에요. 최신 수집본으로 확인하려면 다시 조회하세요" 안내만 붙인다 (자동 재조회·자동 갱신 없음). 다시 조회해 저장하면 **새 메모**가 된다.

### 17-9. 수정·동시 수정·입력 보호

- **수정 권한 [확정 R1]**: 개발용 팀 공유 정책(`db_rules.md` 3-5)에 따라 **로그인한 팀 전체**가 메모를 수정할 수 있다. 서버가 마지막 수정자(`updated_by`)·시각(`updated_at`)·`revision` 을 기록한다. 운영 권한 체계가 정해지면 그 규칙을 따른다.
- **수정 가능한 것 [확정 R1]**: `memo`, `target_country`, `target_region` 만. 조회 원문·출처 사본(`lookup_snapshot`·`regulation_text`)과 상태·성분·유형은 **수정하지 않는다** → 근거가 바뀌면 새 메모. 이유: 이미 요청서에 반영된 사본과 원본 메모의 근거가 다른 수집본이 되는 일을 막고, "사용자가 본 원문" 을 그대로 남긴다.
- **수정 이력 [확정 R1]**: 전체 수정 이력 보관·이전 내용 복구 기능은 **두지 않는다.** 남는 것은 현재 값과 작성자·마지막 수정자·시각·`revision` 뿐이다. 요청서에 반영된 시점의 내용은 반영 사본(`version_links.applied_values`)에 남는다 ([확정] `db_rules.md` 5-1).
- **동시 수정 [확정 R1 원칙 / 방식 제안]**: 자동 덮어쓰기 없이 사용자 입력을 유지한다. 방식은 `revision` 비교 (임시저장 `api_contract.md` 6-4, 최종본 `db_rules.md` 4-2 와 같은 원칙). 서버는 한 트랜잭션에서 `SELECT … FOR UPDATE` → `revision` 비교 → 다르면 409 `note_conflict` + 현재 값, 같으면 UPDATE(`revision + 1`, `updated_by`, `updated_at`). 삭제도 같은 `expected_revision` 비교를 한다 (17-10).
  - 409 화면: 내가 쓴 메모를 **지우지 않고** 그대로 두고, 다른 사람이 저장한 현재 메모·대상을 옆에 보여 준다. 사용자가 합쳐서 다시 저장하거나 취소한다. 자동 병합·자동 덮어쓰기 없음.
- **저장 중 오류**: 모든 오류에서 편집기 입력·체크한 행 유지, 버튼은 처리 중 비활성(중복 저장 방지 — `Common.api` 는 409·503 을 재전송하지 않음, `api_contract.md` 1-2 4번).
- **프로젝트 변경** (공통 프로젝트 바 `ProjectBar.setGuard`): 저장하지 않은 메모 편집기가 열려 있을 때 다른 프로젝트·고객사를 고르면 확인을 묻는다. 취소 → 선택 되돌림·입력 유지. 확인 → **메모 편집기만** 닫는다(조회 결과·파일 결과는 프로젝트와 무관하므로 유지). 편집기를 연 뒤 저장 대상은 연 시점의 연결 프로젝트이며, 편집기에 `고객사 › 프로젝트` 를 표시한다.
- **페이지 이탈**: 저장하지 않은 메모가 있으면 브라우저 기본 이탈 확인만 둔다 (`beforeunload`). 내용을 브라우저·서버에 따로 보관하지 않는다 — 대체 임시저장 아님 (17-1).
- **보관된 프로젝트 [제안]**: 조회·열람은 허용, 만들기·수정·삭제는 400 `project_archived` (정식 저장과 같은 정책 `api_contract.md` 2-1). 임시저장의 예외 규칙(`db_rules.md` 3-7 7번)은 메모에 적용하지 않는다.

### 17-10. 권한·삭제 규칙

| 항목 | 기존 공통 계약 (R1 전) | R1 이후 |
|---|---|---|
| 조회·작성 범위 | 로그인한 팀 사용자 전체가 프로젝트·저장본을 공유 (개발용 기본 정책, `db_rules.md` 3-5). 운영 권한 체계 별도 | 같음 — 팀 전체가 모든 프로젝트 메모를 보고 만든다 |
| 수정 권한 | 메모는 "수정 가능" 만 정해짐 | **[확정 R1]** 팀 전체 수정 + `updated_by`·`updated_at`·`revision` 기록 (17-9) |
| 작성자·시각 | 서버 세션 사용자 [확정] | 같음 |
| 반영된 메모 삭제 | 불가 (`ON DELETE RESTRICT`) [확정] | 같음 — 유지 |
| 반영 전 메모 삭제 **방식** | **미정** (`data_contract.md` 1-5, `db_rules.md` 8-9 "DELETE 여부는 미정") | **[확정 R1]** 삭제 버튼 + 확인 절차 후 **실제 삭제**(DELETE). 보관(`archived_at`) 방식은 쓰지 않는다 |
| 반영 전 메모 삭제 **주체** | **확정 규칙 없음** (2026-11-13 공통 문서 확인 — `data_contract.md`·`db_rules.md`·`api_contract.md` 어디에도 메모 삭제 주체 규칙 없음) | **[제안] 작성자만 삭제** (`created_by` = 세션 사용자). 다른 사람은 403 `note_delete_forbidden`. **"팀 전체 수정" 결정을 "팀 전체 삭제" 로 넓혀 해석하지 않는다** — 수정은 현재 값·`revision` 으로 흔적이 남지만 삭제는 되돌릴 수 없기 때문. 최종 결정은 17-14 |

**삭제 절차 [확정 R1 방식 / 세부 제안]**
1. 화면: 상세·목록에서 [삭제] → 확인 Modal (예: "이 메모를 삭제할까요? 삭제하면 되돌릴 수 없어요." — 문구는 제안). 확인할 때만 `DELETE` 를 보낸다.
2. 반영된 메모(`applied: true`)는 삭제 버튼을 막고 이유를 보여 준다 ("개발요청서에 반영된 메모는 삭제할 수 없어요. 내용 수정은 할 수 있어요."). 서버도 다시 확인한다.
3. 서버: 한 트랜잭션에서 `SELECT … FOR UPDATE` → 프로젝트 보관(400 `project_archived`) → `expected_revision` 비교(409 `note_conflict`, 다른 사람이 그사이 수정했으면 지우지 않음) → 삭제 주체(403 `note_delete_forbidden`, [제안]) → `version_links` 참조 확인(409 `note_referenced`) → `DELETE` → 커밋.
4. **동시 반영과의 경합**: 요청서 저장이 같은 메모를 반영하는 순간 삭제가 들어와도 `version_links.source_note_id` FK(`ON DELETE RESTRICT`)가 최종 보장한다. 반영이 먼저 커밋되면 삭제는 FK 위반 → 409 `note_referenced` 로 바꿔 돌려준다. 삭제가 먼저 커밋되면 요청서 저장은 출처 메모가 없어 실패(400 `invalid_link_source`, 요청서 입력 유지)한다.
5. 삭제 실패 시 화면의 메모 내용은 그대로 둔다.

**앱 역할 권한 (변경안 — 실제 권한 변경은 하지 않음, R2 마이그레이션에서)**
- `GRANT SELECT, INSERT, DELETE ON regulatory_notes TO cosmoa_app;`
- `GRANT UPDATE (memo, target_country, target_region, revision, updated_by, updated_at) ON regulatory_notes TO cosmoa_app;` — 조회 근거 열·`project_id`·`created_*`·`note_type`·`origin` 은 UPDATE 권한에서 뺀다.
- REFERENCES·TRUNCATE·TRIGGER 는 주지 않는다.
- 이것은 앱 역할 DELETE 를 `tab_drafts` 밖으로 넓히는 **두 번째 제한된 예외**다 (`db_rules.md` 8-9). 기존 표(`tab_versions`·`final_history`·`version_links`·`customers`·`projects` 등)에는 넓히지 않는다. 같은 PR 에서 `db_admin.APP_TABLE_PRIVILEGES`·`APP_UPDATE_COLUMNS` 와 `app-role check` 기준을 고친다.
- "작성자만 삭제" 는 앱 역할이 팀 공용이라 DB 권한으로 구분할 수 없다 → **서버 코드가** 세션 사용자로 확인한다. 반영된 메모 보호는 DB FK 가 보장한다.
- `version_links` 에 `source_note_id` 를 넣을 때 FK 검사에 앱 역할의 `regulatory_notes` REFERENCES 권한은 필요 없다고 본다 (REFERENCES 는 FK 를 **만드는** 마이그레이션 역할에 필요). R2 test DB 에서 실제로 확인한다.

- 운영 권한 체계가 정해지면 그 규칙을 따른다. 이 표를 운영 정책으로 확정하지 않는다.

**요청서 담당과 협업할 범위 (이번에 개발요청서 코드는 고치지 않음)**
1. 요청서 화면이 쓸 API: 17-7 의 목록·상세 (같은 프로젝트 메모만 반영 후보). 삭제된 메모는 목록에 없고, 반영 저장 때 없으면 요청서 저장이 실패한다 (17-10 4번).
2. 공통 저장 API 2-1 `links` 항목에 `{"source_note_id": 31, "note_revision": 2, "applied_values": {"target_field": "…", "inserted_text": "…"}}` 형식 추가 — 공통 파일(`versions*.py`) 변경이므로 김민 PM·유정현과 조율.
3. 마이그레이션 (17-12): `regulatory_notes` + `version_links.source_note_id`·"출처는 정확히 하나" CHECK + 권한.
4. 반영 문구를 요청서의 어느 필드에 넣을지(예: R&D 확인 요청사항)는 요청서 담당이 정한다.

### 17-14. 결정 사항과 남은 결정

**R1 에서 결정됨 (2026-11-13)**

| 항목 | 결정 | 반영 위치 |
|---|---|---|
| 메모 대상 | `target_country`(유효한 ISO 국가 코드) 또는 `target_region`(EU·ASEAN) 중 하나, 미지정 허용, 여러 국가는 메모를 나눔. 조회 시장과 구분하고, 대상을 바꿔도 근거의 적용 국가가 바뀐 것처럼 표시하지 않음 | 17-4, `data_contract.md` 1-5 |

**아직 결정이 필요한 사항 (1개)**

1. **반영 전 메모의 삭제 주체** — 공통 문서에 확정 규칙이 없다 (2026-11-13 확인). 추천 [제안]: **작성자만 삭제**. 수정은 현재 값·`revision`·마지막 수정자로 흔적이 남지만 삭제는 되돌릴 수 없고, 수정 이력 기능도 두지 않기로 했기 때문이다. 대안: 팀 전체 삭제 (작성자 부재 시 정리 가능, 대신 다른 사람 메모가 확인 절차만으로 사라짐). "팀 전체 수정" 결정을 이 항목의 결정으로 보지 않는다. 결정 전까지 R2 마이그레이션은 영향이 없다 (DB 권한은 같고, 구분은 서버 코드) — **R3 서버 구현 전에** 정한다.
